## EPIC 12 — Datos que la UI promete y la API no entrega

Son bugs difíciles de ver porque la pantalla renderiza sin errores: no hay 500, no hay stack, no hay caret rojo — solo campos que salen a cero, links que caen a `#`, secciones que dicen "Sin análisis disponible" cada vez. Cada uno requiere alinear el shape con el backend antes de tocar código.

### 12.1 — `CandidateDetailsModal` está desconectado a nivel de contrato

**Archivo:** `src/components/modals/CandidateDetailsModal.jsx` · **Consumido por:** `Resultados.tsx`, `AdvancedResults.tsx`.

**Estado real:** el modal es la pantalla que promete "el corazón" del producto (score breakdown detallado + análisis IA + descarga de CV), pero **casi todos los campos que lee no existen en los tipos ni en la doc §5**. Compila, se abre, y muestra:

| Sección | Campo leído | ¿Existe? | Resultado hoy |
| --- | --- | --- | --- |
| 6 barras del "Desglose del score" | `data.hardSkillsScore`, `data.experienceScore`, `data.roleScore`, `data.languagesScore`, `data.educationScore`, `data.softSkillsScore` | ❌ Ninguno en `MatchResult` | Todas rinden `0/30`, `0/20`, `0/15`, `0/15`, `0/10`, `0/10` |
| "Análisis Detallado" | `data.matchReasoning \|\| data.summary` | ❌ | Siempre `"Sin análisis disponible."` |
| Cabecera | `person.role`, `person.yearsExperience` | ❌ En `Candidate` | Siempre `"Candidato • 0 años exp."` |
| "Descargar CV completo" (footer) | `person.document?.cloudinaryUrl \|\| person.fileUrl` | ❌ El campo real es `Candidate.resumeUrl` | Link muerto (`href=""`) |
| Skills técnicas | `normalized.technicalSkills \|\| person.technicalSkills \|\| person.skills` | Parcial: solo `person.skills` existe | Renderiza si el backend puebla `skills` |

**Bloqueo:** no se puede corregir "solo el frontend". Necesita alineación con el equipo backend sobre qué expone realmente `MatchResult` y `/candidates/:id`. Dos rutas:

1. **Backend expone el desglose.** Añadir a `MatchResult` (o a un tipo `MatchDetail` de `/candidates/:id`) los campos `hardSkillsScore`, `experienceScore`, `roleScore`, `languagesScore`, `educationScore`, `softSkillsScore`, `matchReasoning`. El frontend consume tal cual.
2. **Backend no expone el desglose.** Eliminar las 6 barras y la sección "Análisis Detallado" del modal; dejar solo score global + skills + link a CV. Esta ruta es honesta con el usuario y desbloquea el sprint.

**Pasos (después de decidir la ruta):**

- Si ruta 1: extender `types/api.types.ts` con `MatchDetail` y consumir `candidatesApi.getById(matchId)` al abrir el modal.
- Si ruta 2: podar `CandidateDetailsModal.jsx` líneas 95–101 (barras) y 163–172 (análisis), simplificar el footer para usar `person.resumeUrl`.
- En cualquier caso: migrar el modal a `.tsx` — hoy es `.jsx` sin tipos y usa `parseArray()` defensivo para strings/arrays porque no sabe qué llega.

**✅ Criterio:** al abrir el modal para un candidato real, todo lo que se ve es dato real. Si algo no existe, no se pinta la sección.

### 12.2 — `HistoryTable` busca el link del CV en campos que no existen

**Archivo:** `src/components/HistoryTable.jsx:42-43` · **Consumido por:** `CVHistory.jsx`.

**Estado real:** la tabla del historial de CVs busca la URL del PDF así:

```js
const fileUrl = cv.fileUrl
    || cv.cvUrl
    || (cv.rawApiPayload && (cv.rawApiPayload.cvUrl || cv.rawApiPayload.fileUrl));
```

El campo real que el tipo `Candidate` expone (`api.types.ts:59`) es **`resumeUrl`**. Ninguna de las 4 claves del fallback lo cubre. En el mejor caso el `rawApiPayload` que la API §5.1 dice devolver contiene algo útil, pero es adivinar.

**Consecuencia:** el botón "Ver CV" cae a `href="#"` (línea 71) y `onClick` lo cancela con `preventDefault`. **Todo el link está muerto.**

**Pasos:**

1. Cambiar el orden de fallback a `cv.resumeUrl || cv.fileUrl || cv.rawApiPayload?.cvUrl`.
2. Migrar `HistoryTable.jsx` a `.tsx` con `data: Candidate[]` para que TypeScript detecte el error a futuro.
3. Verificar contra un candidato real de backend que el link abre efectivamente el PDF.

**✅ Criterio:** click en "Ver CV" abre el PDF del candidato en una pestaña nueva.

### 12.3 — "Contratar" no contrata: cierra la vacante entera

**Archivos:** `src/pages/Resultados.tsx:63-81`, `src/pages/AdvancedResults.tsx:124-140`.

**Estado real:** el botón "Contratar" ejecuta `vacanciesApi.updateStatus(id, "CLOSED")` — es decir, marca la **vacante** como cerrada. El candidato específico **no se persiste como contratado** en ningún sitio (el backend no tiene endpoint para marcar candidato — nota en `candidates.api.ts:15-19`). Peor: el toast de éxito dice "Candidato contratado y vacante cerrada con éxito" (`Resultados.tsx:74`), lo que implica un vínculo que no existe.

Esta decisión ya se cerró en P1 6.3 como diseño consciente (backend no tiene endpoint), pero **el copy de la UI sigue prometiendo lo que no hace**. Es una brecha de honestidad, no de código.

**Pasos:**

1. Reemplazar el label del botón "Contratar" por algo como "Cerrar vacante" o "Marcar como cubierta".
2. Reemplazar el confirm "Contratar cerrará la vacante..." por "¿Cerrar esta vacante como cubierta? Ya no aceptará nuevos candidatos."
3. Reemplazar el toast por "Vacante cerrada."
4. Si el equipo backend acepta añadir un endpoint `PATCH /candidates/:id/hire`, revertir todo esto y wirear al endpoint real.

**✅ Criterio:** el copy de la UI describe la acción real (cerrar vacante), no una acción inventada (contratar candidato).

## EPIC 13 — Validación del sprint anterior

### 13.1 — Verificación manual en navegador de P2 + P3

**Contexto:** el CLAUDE.md exige _"For UI or frontend changes, start the dev server and use the feature in a browser before reporting the task as complete."_ Los 10 commits de la sesión anterior (`0a34682`…`f6feba2`) pasaron `tsc` y `vite build`, pero **ninguno se probó en `npm run dev`**. Sin este paso, todo el trabajo de P1/P2/P3 vive en un estado "compila, pero no sé si se ve".

**Flujos a verificar contra un backend real:**

1. **Login → redirect por rol** (commit `b7dac91`). Después de unificar el casing a `ADMIN`/`USER`, cualquier sesión en `localStorage` con formato viejo (`role: "admin"`) se invalida en `readStoredSession`. Confirmar:
   - Login limpio con usuario `ADMIN` redirige a `/admin`.
   - Login limpio con usuario `USER` redirige a `/dashboard`.
   - Una sesión persistida en formato viejo cae de vuelta a `/login` sin blank-page.
2. **Panel Admin** (`0a34682` + `36ba52b`):
   - `GET /admin/stats` se llama y las 6 tarjetas pintan valores reales.
   - Paginación de `GET /admin/users` funciona (query `?page=&limit=`).
   - Cambiar rol persiste tras el refetch (verificar en Network).
   - El botón "Eliminar" ahora dispara `DELETE /admin/users/:id`, refetchea y el usuario desaparece.
   - El confirm del delete se puede cancelar sin lanzar la request.
3. **Sidebar** (`002d7f7`): "Panel Admin" aparece dentro del primer grupo solo si `user.role === "ADMIN"`. Un `USER` no ve el link.
4. **Dashboard** (`0de2a00`): `GET /dashboard` se llama al montar; loading, error y empty se ven bien; el eje Y ya no está fijo en 14; los meses "YYYY-MM" salen como "Ene"/"Feb".
5. **MetricCard como Link** (`5fcade4`): click en cualquier tarjeta del Dashboard navega a su historial.
6. **LoginForm** (`e52d9ba`): con contraseña oculta se ve `Eye`; al hacer click y mostrarla, se ve `EyeOff`.
7. **Historiales sin `alert()`** (`eee7b20`): forzar un fallo en `DELETE /positions/:id`, `DELETE /vacancies/:id`, `PATCH /vacancies/:id/status`, `PUT /departments/:id`, `DELETE /departments/:id` — cada error debe mostrar el banner rojo inline arriba de la lista, no un popup nativo.

**✅ Criterio:** los 7 flujos verificados en dev server contra backend real. Screenshots opcionales en `docs/es/last-changes.md`.
