## EPIC 8 — Panel de Administración

Archivos: `src/pages/AdminPanel.tsx`, `src/services/api/admin.api.ts`, `src/components/admin/*`, `src/types/admin.types.ts`.
API: §6 — **admin-only** (`role: ADMIN`, si no `403`).

### 8.1 — ⚠️ Reescribir `admin.api.ts`: hoy es un simulacro

**Este es el ítem más urgente del backlog completo**, por encima de varios P1: la pantalla **aparenta funcionar**, así que el bug es invisible en una demo.

**Estado actual (`src/services/api/admin.api.ts`):**

- **No importa `apiClient`.** Ni una sola llamada HTTP.
- Exporta `adminService` con un array `MOCK_USERS` (Ana Garcia, Carlos Perez, Beatriz Solis) y `setTimeout` para simular latencia.
- `getStats()` devuelve números inventados (`totalUsers: 145`, …) y está tipado `Promise<any>` → viola `@typescript-eslint/no-explicit-any`.
- `updateRole()` y `deleteUser()` resuelven `{ success: true }` sin persistir nada, y hacen `console.log`.

Los endpoints admin **no** usan `sendResponseOr404`, así que `apiClient` desempaqueta `.data` normal.

```ts
import { apiClient } from "./apiClient";
import { User } from "../../types/api.types";

interface AdminStats {
  usersCount: number;
  candidatesCount: number;
  positionsCount: number;
  vacanciesCount: number;
  activeVacancies: number;
  closedVacancies: number;
}

interface AdminUsersPage {
  users: User[];
  meta: { totalCount: number; currentPage: number; totalPages: number };
}

export const adminService = {
  getStats: (): Promise<AdminStats> =>
    apiClient<AdminStats>("/admin/stats", { method: "GET" }),

  getUsers: (page = 1, limit = 50): Promise<AdminUsersPage> =>
    apiClient<AdminUsersPage>(`/admin/users?page=${page}&limit=${limit}`, { method: "GET" }),

  updateRole: (id: number | string, role: "ADMIN" | "USER"): Promise<User> =>
    apiClient<User>(`/admin/users/${id}/role`, {
      method: "PUT",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({ role }),
    }),

  deleteUser: (id: number | string): Promise<void> =>
    apiClient<void>(`/admin/users/${id}`, { method: "DELETE" }),
};
```

> **Ojo con la forma de la respuesta:** el `getUsers` real devuelve `{ users, meta }`, no un `AdminUser[]` plano como el mock. `UserTableModule`, `RoleUpdateModule` y `UserDeleteModule` hoy asumen un array — habrá que adaptarlos (o normalizar en el servicio, como hace `departmentsApi`).

> **Ojo con `StatItem`:** `StatsModule` espera `StatItem[]` (con `label`, `icon`, `type`), pero la API devuelve un objeto plano de contadores. La transformación a tarjetas es responsabilidad del front.

**✅ Criterio:** abrir la pestaña de red del navegador y ver peticiones reales a `/admin/*`.

3. Adaptar los módulos a la forma real `{ users, meta }` (ver 8.1) y refrescar la lista tras cada acción.
4. Estados de error/empty (hoy solo hay loading).
5. Quitar el `console.log` de `RoleUpdateModule.tsx:41`.

### 8.3 — Casing de roles

**Problema:** la API usa `ADMIN`/`USER`; `admin.types.ts` tipa `'admin' | 'user'`, y `AuthContext.UserData.role` también.

Hoy funciona por dos parches defensivos (`normalizeRole()` en `Login.tsx`, `.toLowerCase()` en `AdminRoute`). Cualquier comparación nueva sin normalizar fallará en silencio.

**Pasos:** unificar al enum del backend (`ADMIN`/`USER`) en `AdminUser.role` y `UserData.role`, y mapear a etiqueta visible ("Admin"/"Usuario") en la UI. Ajustar `normalizeRole` y `AdminRoute` en consecuencia.

---

### 8.4 — No confundir stats globales con dashboard

`GET /admin/stats` es **global** (toda la plataforma); `GET /dashboard` es por usuario (§9.4). Mantenerlos como fuentes separadas; el panel admin usa `/admin/stats`.

**✅ Criterio EPIC 8:** el panel lista usuarios reales (paginados), permite cambiar rol y eliminar, y muestra stats globales.

## EPIC 9 — Auth / control por rol

Archivos: `src/components/context/AuthContext.tsx`, `src/pages/Login.tsx`, `src/layouts/Sidebar.tsx`, `src/components/routes/AdminRoute.tsx`.

### 9.1 — ✅ RESUELTO — Guardar el `role` en el AuthContext

`UserData` incluye `role: 'admin' | 'user'`. `login(email, token, role, username?)` lo persiste en `tm_user`. `Login.tsx` lo extrae de `data.user.role`, lo normaliza a minúsculas con `normalizeRole()` antes de guardarlo, y redirige a `/admin` o `/dashboard` según el rol.

> Pendiente de unificar el casing — ver **8.3**.

### 9.2 — Sidebar: admin primero, con ícono propio y solo para ADMIN

**Archivo:** `src/layouts/Sidebar.tsx` (~líneas 55-60).

**Estado actual:** el item "Administración" sigue en el **último** grupo ("CONFIGURACIÓN"), usa `Icons.sidebar.dashboard` (el mismo ícono que Dashboard) y **se renderiza para todos los usuarios**. Como `AdminRoute` ya protege la ruta, un usuario normal ve el enlace, lo pulsa y rebota a `/dashboard`: es seguro, pero confuso.

**Pasos:**

1. Mover el item "Administración" al primer grupo del menú, según el mockup.
