## EPIC 7 — Dashboard

Files: `src/pages/Dashboard.tsx`, `src/components/cards/MetricCard.tsx`.
API: §7 (`GET /dashboard`, user-scoped).

### 7.1 — Connect to the real API

**Problem:** the Dashboard uses a full `MOCK_DATA`, never `dashboardService.getSummary()`.

**Groundwork ready:** `dashboardService.getSummary()` already returns `DashboardSummary` (the real backend typing). `src/types/dashboard.types.ts` exposes `DashboardTotals`, `VacancyStatusBreakdownItem`, `MonthlyActivityItem`.

**Steps:**

1. Load on mount:
   ```ts
   const [summary, setSummary] = useState<DashboardSummary | null>(null);
   const [loading, setLoading] = useState(true);
   useEffect(() => {
     dashboardService.getSummary()
       .then(setSummary)
       .catch(console.error)
       .finally(() => setLoading(false));
   }, []);
   ```
2. Map the response:
   - **Metrics (`MetricCard`):** from `summary.total` → Total Positions=`positionsCount`, Departments=`departmentsCount`, Candidates=`candidatesCount`, Open Vacancies=`openVacanciesCount`.
   - **Vacancy statuses:** from `summary.vacancyStatusBreakdown[]` (`status`, `count`, `percentage`). Map `ACTIVE/PAUSED/CLOSED` to a label ("Abiertas/Pausadas/Cerradas") and a color. Can be transformed into `DashboardVacancyStatusCard[]` (existing UI interface).
   - **Monthly chart:** from `summary.monthlyActivity[]` — `month` ("2026-01" → "Ene"), `positionsCreated`, `cvUploads`, `vacanciesCreated`. Compute `MAX_Y_VALUE` dynamically (currently hardcoded to 14).
3. Loading/error/empty states (none today).
4. Once connected, decide what to do with `DashboardStats`/`MonthlyData` (the mock's interfaces): either make them the view model behind an adapter, or delete them.

**✅ Criterion:** metrics and charts with the user's real data.

## EPIC 8 — Admin Panel

Files: `src/pages/AdminPanel.tsx`, `src/services/api/admin.api.ts`, `src/components/admin/*`, `src/types/admin.types.ts`.
API: §6 — **admin-only** (`role: ADMIN`, otherwise `403`).

### 8.1 — ⚠️ Rewrite `admin.api.ts`: it is currently a simulation

**This is the single most urgent item in the whole backlog**, ahead of several P1s: the screen **appears to work**, so the bug is invisible in a demo.

**Current state (`src/services/api/admin.api.ts`):**

- **It does not import `apiClient`.** Not a single HTTP call.
- Exports `adminService` with a `MOCK_USERS` array (Ana Garcia, Carlos Perez, Beatriz Solis) and `setTimeout` to simulate latency.
- `getStats()` returns invented numbers (`totalUsers: 145`, …) and is typed `Promise<any>` → violates `@typescript-eslint/no-explicit-any`.
- `updateRole()` and `deleteUser()` resolve `{ success: true }` without persisting anything, and `console.log`.

The admin endpoints do **not** use `sendResponseOr404`, so `apiClient` unwraps `.data` normally.

```ts
import { apiClient } from "./apiClient";
import { User } from "../../types/api.types";

interface AdminStats {
  usersCount: number;
  candidatesCount: number;
  positionsCount: number;
  vacanciesCount: number;
  activeVacancies: number;
  closedVacancies: number;
}

interface AdminUsersPage {
  users: User[];
  meta: { totalCount: number; currentPage: number; totalPages: number };
}

export const adminService = {
  getStats: (): Promise<AdminStats> =>
    apiClient<AdminStats>("/admin/stats", { method: "GET" }),

  getUsers: (page = 1, limit = 50): Promise<AdminUsersPage> =>
    apiClient<AdminUsersPage>(`/admin/users?page=${page}&limit=${limit}`, { method: "GET" }),

  updateRole: (id: number | string, role: "ADMIN" | "USER"): Promise<User> =>
    apiClient<User>(`/admin/users/${id}/role`, {
      method: "PUT",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({ role }),
    }),

  deleteUser: (id: number | string): Promise<void> =>
    apiClient<void>(`/admin/users/${id}`, { method: "DELETE" }),
};
```

> **Watch the response shape:** the real `getUsers` returns `{ users, meta }`, not a flat `AdminUser[]` like the mock. `UserTableModule`, `RoleUpdateModule`, and `UserDeleteModule` currently assume an array — they will need adapting (or normalize in the service, as `departmentsApi` does).

> **Watch `StatItem`:** `StatsModule` expects `StatItem[]` (with `label`, `icon`, `type`), but the API returns a flat counter object. Transforming it into cards is the frontend's job.

**✅ Criterion:** open the browser's network tab and see real requests to `/admin/*`.

### 8.3 — Role casing

**Problem:** the API uses `ADMIN`/`USER`; `admin.types.ts` types `'admin' | 'user'`, and so does `AuthContext.UserData.role`.

It works today thanks to two defensive patches (`normalizeRole()` in `Login.tsx`, `.toLowerCase()` in `AdminRoute`). Any new comparison without normalizing will fail silently.

**Steps:** unify on the backend enum (`ADMIN`/`USER`) in `AdminUser.role` and `UserData.role`, and map to a display label ("Admin"/"Usuario") in the UI. Adjust `normalizeRole` and `AdminRoute` accordingly.

---

### 8.4 — Don't confuse global stats with the dashboard

`GET /admin/stats` is **global** (whole platform); `GET /dashboard` is per user (§9.4). Keep them as separate sources; the admin panel uses `/admin/stats`.

**✅ EPIC 8 criterion:** the panel lists real (paginated) users, allows changing roles and deleting, and shows global stats.

## EPIC 9 — Auth / role-based access

Files: `src/components/context/AuthContext.tsx`, `src/pages/Login.tsx`, `src/layouts/Sidebar.tsx`, `src/components/routes/AdminRoute.tsx`.

### 9.1 — ✅ RESOLVED — Store the `role` in AuthContext

`UserData` includes `role: 'admin' | 'user'`. `login(email, token, role, username?)` persists it in `tm_user`. `Login.tsx` extracts it from `data.user.role`, normalizes it to lowercase with `normalizeRole()` before storing, and redirects to `/admin` or `/dashboard` based on it.

> Casing still needs unifying — see **8.3**.

---

### 9.2 — Sidebar: admin first, with its own icon, and only for ADMIN

**File:** `src/layouts/Sidebar.tsx` (~lines 55-60).

**Current state:** the "Administración" item is still in the **last** group ("CONFIGURACIÓN"), uses `Icons.sidebar.dashboard` (the same icon as Dashboard), and is **rendered for every user**. Since `AdminRoute` already guards the route, a normal user sees the link, clicks it, and bounces to `/dashboard`: secure, but confusing.

**Steps:**

1. Move the "Administración" item to the first menu group, per the mockup.
2. Give it its own icon (e.g. lucide's `Shield`) instead of `Icons.sidebar.dashboard`.
3. Render it only when `user?.role === "admin"` (via `useAuth()`, which the Sidebar already consumes).

---

### 9.3 — ✅ RESOLVED — Protect the `/admin` route

`src/components/routes/AdminRoute.tsx` wraps `/admin` inside `ProtectedRoute`. No user → `/login`; non-admin role → `/dashboard`. Avoids the backend's raw `403`.

> ⚠️ **Clean up before calling it closed:** it contains two debug `console.log` calls that dump the whole `user` object to the console on every render (see [`P3.md`](./P3.md) §10.5).

**✅ EPIC 9 criterion:** after login the role is available; "Administración" appears first, with its own icon, and only for administrators.
