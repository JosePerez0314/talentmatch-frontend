## EPIC 14 — UI robustness

### 14.1 — `CandidatesHistory` renders the raw enum

**File:** `src/pages/CandidatesHistory.tsx:115`.

**Problem:** the status badge renders `{candidate.status}` directly — the user sees `DISPONIBLE` or `CONTRATADO` in all caps. The convention across the rest of the app (after P2 8.3 turned `ADMIN`/`USER` into `Admin`/`Usuario`) is to map enums to human labels at render time.

**Steps:**

- Create `STATUS_LABELS: Record<CandidateStatus, string> = { DISPONIBLE: "Disponible", CONTRATADO: "Contratado" }`.
- Use `STATUS_LABELS[candidate.status]` in the badge.

**✅ Criterion:** the user sees "Disponible" / "Contratado", not `DISPONIBLE` / `CONTRATADO`.

### 14.2 — Sidebar: "Acme Corp" fallback

**File:** `src/layouts/Sidebar.tsx:75`.

**Problem:** `const displayName = user?.username || "Acme Corp";` — if a user has an empty `username` (e.g. if `deriveUsername` in `AuthContext` returned something odd), the sidebar shows a random company name.

**Steps:**

- Replace `"Acme Corp"` with a neutral fallback: empty string, `user?.email`, or `"—"`.
- Adjust the `initialLetter` logic so it doesn't crash on an empty string.

**✅ Criterion:** the sidebar never shows "Acme Corp" as the session brand.

### 14.3 — `DepartmentHistory` with an invented date

**File:** `src/pages/DepartmentHistory.tsx:134`.

**Problem:** `Creado: {dept.createdAt ? new Date(dept.createdAt).toLocaleDateString() : "01/01/2026"}` — if the backend doesn't return `createdAt`, a fixed date shows up that a user could believe is real.

**Steps:**

- Change the `"01/01/2026"` fallback to `"—"` or `"Unknown date"`.

**✅ Criterion:** no row in the history shows a fake date.

### 14.4 — `UploadCV` filters to `ACTIVE` without explanation

**File:** `src/pages/UploadCV.tsx:37`.

**Problem:** the destination vacancy dropdown excludes `PAUSED` and `CLOSED`. Docs §4 don't restrict upload by state. If the backend allows uploading CVs to a `PAUSED` vacancy (which is a temporary pause, not a close), that option is being silently dropped.

**Steps:**

- Check with the backend which states accept uploads.
- Adjust the filter (probably accept `ACTIVE` and `PAUSED`, not only `ACTIVE`).
- Or document the restriction in the "No active vacancies" message.

**✅ Criterion:** the filter matches what the backend accepts and the empty message explains it.

---

### 14.5 — `AdvancedResults` / `Resultados`: silent fallback if `getById` fails

**Files:** `src/pages/AdvancedResults.tsx:68-75`, `src/pages/Resultados.tsx:36-43`.

**Problem:** both screens run `Promise.all([getResults, getById.catch(() => null)])`. If `getById` fails (404, network down), `vacancy` stays `null` and the header shows a generic `"Vacancy"` without warning the user that the vacancy detail is missing.

**Steps:**

- Distinguish `vacancy === null` from "loading" and render a small notice ("Vacancy detail failed to load") instead of a silent fallback.

**✅ Criterion:** a partial failure is visible; the user doesn't think the vacancy is named "Vacancy".

## EPIC 15 — Dashboard responsive

### 15.1 — Fixed `min-h` + breakpoint verification

**File:** `src/pages/Dashboard.tsx` (~line 158 after the wiring from the previous sprint).

**Problem:** the chart block still has a fixed `min-h-[350px] xl:min-h-[450px]`. On small screens it forces horizontal scroll and doesn't collapse well on mobile. This item came from the previous sprint (was P4 11.1, and before that P2 7.2) and was deliberately left out of "data connections".

**Steps:**

- Test at 360 px, 768 px, 1024 px, 1440 px without horizontal scroll.

**✅ Criterion:** the Dashboard renders without unintended scroll on mobile, tablet, laptop and desktop.

## EPIC 16 — Consistent pagination

### 16.1 — `vacanciesApi.getResults` drops `meta`

**File:** `src/services/api/vacancies.api.ts:65-67`.

**Problem:** docs §4 say `GET /vacancies/:id/results` responds with `{ success, data: MatchResult[], meta: { total, page, limit, totalPages } }`. The service does `apiClient<MatchResult[]>(...)` — it keeps `.data` (or `.response.data` because of the double envelope) and **discards `meta`**. Neither `Resultados` nor `AdvancedResults` can paginate past the first 20 candidates.

**Steps:**

- Create a `PaginatedResults = { results: MatchResult[]; meta: { total, page, limit, totalPages } }` type.
- Change `getResults` to return `PaginatedResults`.
- Wire pagination controls in `Resultados` and `AdvancedResults`.

**⚠️ Note:** `apiClient` only unwraps `.data`. You'll need `raw: true` or a different call site to keep `meta`.

**✅ Criterion:** the results screens support more than 20 candidates.

---

### 16.2 — `candidateService.getAll` doesn't accept pagination

**File:** `src/services/api/candidates.api.ts:6-11`.

**Problem:** `GET /candidates` may paginate on the backend (not explicitly documented, but expected for a list endpoint), but the service sends a raw request without `page`/`limit`. `CVHistory` and `CandidatesHistory` get whatever the backend returns.

**Steps:**

- Confirm with the backend whether `/candidates` accepts `?page=&limit=`.
- If yes: extend the signature like `adminService.getUsers`.

**✅ Criterion:** the frontend can paginate the candidate list if the backend supports it.

---

### 16.3 — `RoleUpdateModule` and `UserDeleteModule` stuck on page 1

**Files:** `src/components/admin/RoleUpdateModule.tsx`, `src/components/admin/UserDeleteModule.tsx`.

**Problem:** in P2 8.2 the `users` state was lifted to `AdminPanel` to enable a post-mutation refetch, but only `UserTableModule` exposes pagination controls. The other two modules see the first 50 users that `AdminPanel` is currently paging through.

On a platform with >50 users, the admin can't change the role or delete users from the whole pool — only from the current page.

**Steps:**

- Add pagination (or server-side search) to `RoleUpdateModule` / `UserDeleteModule`, or
- Wire them to the same pagination as `UserTableModule` (shared `page` in `AdminPanel`).

**✅ Criterion:** the admin can modify/delete any user, not only those on page 1.

## EPIC 17 — Orphan endpoints

### 17.1 — `authService.register` with no sign-up screen

**File:** `src/services/api/auth.api.ts:22-29`.

**Problem:** the `register(RegisterCredentials): Promise<LoginResponse>` method is implemented and typed, but **no component calls it**. `Login.tsx` has no "Register" link. It's either dead code or a half-connected feature.

**Decision:**

- **Option A:** implement the `/register` screen with `RegisterForm`, redirect to the Dashboard on success.
- **Option B:** delete `authService.register` and the `RegisterCredentials` type if there's no plan for in-app registration.

**✅ Criterion:** if `register` exists, something calls it; if not, it doesn't exist.

---

### 17.2 — `GET /candidates/:id` with no consumer

**File:** `src/services/api/candidates.api.ts`.

**Problem:** docs §5 document `GET /candidates/:id`. `candidatesApi` has no `getById`. `CandidatesHistory` is a table with no navigation to a detail; `CandidateDetailsModal` (see P0 12.1) shows info that already comes in `MatchResult`.

**Decision:**

- **Option A:** implement `candidatesApi.getById` and a `/candidates/:id` page with the full profile.
- **Option B:** wire the detail into `CandidateDetailsModal` from `CandidatesHistory` (also fixes P0 12.1 if the endpoint exposes the missing fields).
- **Option C:** leave as-is and document it — the real flow may be "a candidate is only visible as a row in a vacancy's results".

**✅ Criterion:** the endpoint has a consumer or is clearly discarded.
