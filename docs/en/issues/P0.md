## EPIC 12 — Data the UI promises but the API doesn't return

These bugs are hard to see because the page renders without errors: no 500, no stack, no red caret — just fields that resolve to zero, links that fall back to `#`, sections that say "No analysis available" every time. Each one needs a shape alignment with the backend before any code change.

### 12.1 — `CandidateDetailsModal` is disconnected at the contract level

**File:** `src/components/modals/CandidateDetailsModal.jsx` · **Consumed by:** `Resultados.tsx`, `AdvancedResults.tsx`.

**Real state:** the modal is the screen that promises the "heart" of the product (detailed score breakdown + AI analysis + CV download), but **almost every field it reads is missing from the types and the docs (§5)**. It compiles, it opens, and it shows:

| Section | Field read | Exists? | Today's result |
| --- | --- | --- | --- |
| 6 bars of "Score breakdown" | `data.hardSkillsScore`, `data.experienceScore`, `data.roleScore`, `data.languagesScore`, `data.educationScore`, `data.softSkillsScore` | ❌ None on `MatchResult` | All render `0/30`, `0/20`, `0/15`, `0/15`, `0/10`, `0/10` |
| "Detailed Analysis" | `data.matchReasoning \|\| data.summary` | ❌ | Always `"No analysis available."` |
| Header | `person.role`, `person.yearsExperience` | ❌ On `Candidate` | Always `"Candidate • 0 years exp."` |
| "Download full CV" (footer) | `person.document?.cloudinaryUrl \|\| person.fileUrl` | ❌ The real field is `Candidate.resumeUrl` | Dead link (`href=""`) |
| Technical skills | `normalized.technicalSkills \|\| person.technicalSkills \|\| person.skills` | Partial: only `person.skills` exists | Renders if the backend populates `skills` |

**Blocker:** this can't be fixed frontend-only. It needs alignment with the backend team on what `MatchResult` and `/candidates/:id` really expose. Two paths:

1. **Backend exposes the breakdown.** Add `hardSkillsScore`, `experienceScore`, `roleScore`, `languagesScore`, `educationScore`, `softSkillsScore`, `matchReasoning` to `MatchResult` (or to a `MatchDetail` type from `/candidates/:id`). Frontend consumes them as-is.
2. **Backend does not expose the breakdown.** Drop the 6 bars and the "Detailed Analysis" section from the modal; keep only overall score + skills + CV link. This is the honest option and unblocks the sprint.

**Steps (after picking the path):**

- If path 1: extend `types/api.types.ts` with `MatchDetail` and consume `candidatesApi.getById(matchId)` on modal open.
- If path 2: prune `CandidateDetailsModal.jsx` lines 95–101 (bars) and 163–172 (analysis), simplify the footer to use `person.resumeUrl`.
- Either way: migrate the modal to `.tsx` — it's `.jsx` today with no types and uses defensive `parseArray()` for strings/arrays because it doesn't know what arrives.

**✅ Criterion:** when the modal opens for a real candidate, everything you see is real data. If a field doesn't exist, its section doesn't render.

### 12.2 — `HistoryTable` looks for the CV link in fields that don't exist

**File:** `src/components/HistoryTable.jsx:42-43` · **Consumed by:** `CVHistory.jsx`.

**Real state:** the CV history table looks for the PDF URL like this:

```js
const fileUrl = cv.fileUrl
    || cv.cvUrl
    || (cv.rawApiPayload && (cv.rawApiPayload.cvUrl || cv.rawApiPayload.fileUrl));
```

The real field the `Candidate` type exposes (`api.types.ts:59`) is **`resumeUrl`**. None of the 4 fallback keys covers it. In the best case the `rawApiPayload` from API §5.1 contains something useful, but it's guesswork.

**Consequence:** the "View CV" button falls back to `href="#"` (line 71) and `onClick` cancels it with `preventDefault`. **The whole link is dead.**

**Steps:**

1. Change the fallback order to `cv.resumeUrl || cv.fileUrl || cv.rawApiPayload?.cvUrl`.
2. Migrate `HistoryTable.jsx` to `.tsx` typed with `data: Candidate[]` so TypeScript catches the issue in the future.
3. Verify against a real backend candidate that the link actually opens the PDF.

**✅ Criterion:** clicking "View CV" opens the candidate's PDF in a new tab.

### 12.3 — "Hire" doesn't hire: it closes the whole vacancy

**Files:** `src/pages/Resultados.tsx:63-81`, `src/pages/AdvancedResults.tsx:124-140`.

**Real state:** the "Hire" button runs `vacanciesApi.updateStatus(id, "CLOSED")` — i.e. it marks the **vacancy** as closed. The specific candidate is **not persisted as hired** anywhere (the backend has no endpoint to mark a candidate — see the note in `candidates.api.ts:15-19`). Worse: the success toast says "Candidate hired and vacancy closed successfully" (`Resultados.tsx:74`), implying a link that doesn't exist.

This decision was already closed in P1 6.3 as conscious design (backend has no endpoint), but **the UI copy still promises what it doesn't do**. It's a honesty gap, not a code bug.

**Steps:**

1. Replace the "Hire" button label with something like "Close vacancy" or "Mark as filled".
2. Replace the "Hiring will close the vacancy..." confirm with "Close this vacancy as filled? It won't accept new candidates."
3. Replace the toast with "Vacancy closed."
4. If the backend team agrees to add a `PATCH /candidates/:id/hire` endpoint, revert all this and wire to the real endpoint.

**✅ Criterion:** the UI copy describes the real action (close vacancy), not an imagined one (hire candidate).

## EPIC 13 — Previous sprint validation

### 13.1 — Manual browser verification of P2 + P3

**Context:** the CLAUDE.md requires _"For UI or frontend changes, start the dev server and use the feature in a browser before reporting the task as complete."_ The 10 commits from the previous session (`0a34682`…`f6feba2`) passed `tsc` and `vite build`, but **none of them was exercised in `npm run dev`**. Without this step, all P1/P2/P3 work lives in a "compiles, but I don't know if it renders" state.

**Flows to verify against a real backend:**

1. **Login → role-based redirect** (commit `b7dac91`). After unifying casing to `ADMIN`/`USER`, any session in `localStorage` with the old shape (`role: "admin"`) is invalidated by `readStoredSession`. Confirm:
   - A clean login as `ADMIN` redirects to `/admin`.
   - A clean login as `USER` redirects to `/dashboard`.
   - A persisted session in the old shape falls back to `/login` without blanking the page.
2. **Admin Panel** (`0a34682` + `36ba52b`):
   - `GET /admin/stats` is called and the 6 cards render real values.
   - Pagination on `GET /admin/users` works (query `?page=&limit=`).
   - Changing a role persists after the refetch (verify in Network).
   - The "Delete" button now actually fires `DELETE /admin/users/:id`, refetches, and the user disappears from the list.
   - The delete confirm dialog can be cancelled without firing the request.
3. **Sidebar** (`002d7f7`): "Panel Admin" appears inside the first group only when `user.role === "ADMIN"`. A `USER` doesn't see the link.
4. **Dashboard** (`0de2a00`): `GET /dashboard` fires on mount; loading, error and empty states render correctly; the Y axis is no longer pinned at 14; the "YYYY-MM" months show up as "Ene"/"Feb".
5. **MetricCard as Link** (`5fcade4`): clicking any Dashboard card navigates to its history route.
6. **LoginForm** (`e52d9ba`): with the password hidden, the icon is `Eye`; after clicking to reveal, the icon is `EyeOff`.
7. **Histories without `alert()`** (`eee7b20`): force a failure on `DELETE /positions/:id`, `DELETE /vacancies/:id`, `PATCH /vacancies/:id/status`, `PUT /departments/:id`, `DELETE /departments/:id` — each error must show the red inline banner above the list, not a native popup.

**✅ Criterion:** the 7 flows verified in the dev server against a real backend. Screenshots optional in `docs/en/last-changes.md`.
