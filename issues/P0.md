## EPIC 1 — Normalizar el envelope de respuesta en `apiClient`

### Contexto

Muchos GET del backend usan el helper `sendResponseOr404`, que **envuelve la respuesta un nivel extra**: `{ "response": { "success": true, "data": ... } }` en vez de `{ "success": true, "data": ... }` (ver `API_DOCUMENTATION.md` §9.1).

Hoy `apiClient` (`src/services/api/apiClient.ts`) solo mira `castedBody.data` de primer nivel. En la doble envoltura ese `.data` no existe (está en `.response.data`), así que devuelve el objeto crudo `{ response: {...} }`. Consecuencia: **todos los servicios menos `departmentsApi` reciben un objeto que no saben leer → listas vacías** en Posiciones, Vacantes, Candidatos y (al conectar) Dashboard.

~~Además, en el caso 404 de ese helper el backend manda `success: "false"` como **string**, no booleano (§9.2), por lo que un chequeo `=== false` no lo detecta.~~ **Corregido (2026-07-07):** `sendResponseOr404` ahora manda `success: false` como booleano también en el caso 404 (ver `API_DOCUMENTATION.md` §9). El chequeo tolerante a `"false"` (string) descrito en 1.1 ya se quitó de `apiClient`, no era necesario mantenerlo.

### Endpoints con doble envoltura (§9.1)

`GET /positions`, `GET /positions/:id`, `GET /candidates`, `GET /candidates/:id`, `GET /departments/*`, `PUT/DELETE /departments/:id`, `GET /vacancies`, `PATCH /vacancies/:id/status`, `PUT /vacancies/:id`, `GET /dashboard`.
**Excepción:** `GET /vacancies/:id` responde `{ success, data }` directo (sin `response`).

### 1.1 — Centralizar el desempaquetado

**Archivo:** `src/services/api/apiClient.ts`

Reemplazar el bloque final (desde `const castedBody ...` hasta el `return responseBody`) por una normalización que:

1. Si el body trae la clave `response`, opera sobre `body.response`; si no, sobre el body tal cual (esto cubre la excepción de `GET /vacancies/:id` y los endpoints que ya responden plano).
2. Evalúa `success` contemplando `false` (boolean) **y** `"false"` (string).
3. Devuelve `.data` si existe; si no, el objeto normalizado.
4. Los mensajes de error se leen del objeto ya normalizado.

```ts
const responseBody: unknown = isJson ? await response.json() : null;
const rawBody = responseBody as Record<string, unknown> | null;

// Normaliza la doble envoltura de sendResponseOr404: { response: { success, data } }
const envelope: Record<string, unknown> | null =
  rawBody && typeof rawBody === "object" && "response" in rawBody
    ? (rawBody.response as Record<string, unknown> | null)
    : rawBody;

// success puede venir como boolean false o string "false" (caso 404 del helper)
const successFlag = envelope?.success;
const isSuccessFlag = successFlag !== false && successFlag !== "false";

if (!response.ok || !isSuccessFlag) {
  if (response.status === 401) {
    throw new Error("Sesión expirada o no autorizada.");
  }
  const errorMessage = String(
    envelope?.error || envelope?.message || `Error: ${response.status}`,
  );
  throw new Error(errorMessage);
}

// Devuelve data desempaquetada; si no hay data, el objeto normalizado
if (envelope && envelope.data !== undefined) {
  return envelope.data as T;
}
return envelope as T;
```

**Nota sobre login:** `POST /users/login` responde `{ success, token, user }` (sin `data` ni `response`). Con la lógica de arriba, `envelope = rawBody` y como no hay `.data`, devuelve el objeto completo → `Login.tsx` sigue leyendo `data.token` y `data.user`. ✅ No romper este caso al probar.
