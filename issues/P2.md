## EPIC 7 — Dashboard

Archivos: `src/pages/Dashboard.tsx`, `src/components/cards/MetricCard.tsx`.
API: §7 (`GET /dashboard`, scoped al usuario). Respuesta:
```json
{
  "total": { "positionsCount", "departmentsCount", "candidatesCount", "openVacanciesCount" },
  "vacancyStatusBreakdown": [ { "status", "count", "percentage" } ],
  "monthlyActivity": [ { "month", "positionsCreated", "cvUploads", "vacanciesCreated" } ]
}
```

### 7.1 — [Pendiente de conectar] Conectar a la API real

**Problema:** el Dashboard usa `MOCK_DATA` completo, no `dashboardService.getSummary()`.

**Pasos:**
1. Cargar al montar:
   ```ts
   const [stats, setStats] = useState<DashboardStats | null>(null);
   const [loading, setLoading] = useState(true);
   useEffect(() => {
     dashboardService.getSummary()
       .then(setStats)
       .catch(console.error)
       .finally(() => setLoading(false));
   }, []);
   ```
   (Tras EPIC 1, `getSummary` devuelve el objeto desempaquetado.)
2. Mapear la respuesta del backend a lo que consumen los componentes:
   - **Métricas (`MetricCard`):** de `total` → Total Posiciones=`positionsCount`, Departamentos=`departmentsCount`, Candidatos=`candidatesCount`, Vacantes Abiertas=`openVacanciesCount`.
   - **Estados de vacantes:** de `vacancyStatusBreakdown[]` → usar `status`, `count`, `percentage`. Mapear `status` (`ACTIVE/PAUSED/CLOSED`) a label ("Abiertas/Pausadas/Cerradas") y color.
   - **Gráfica mensual:** de `monthlyActivity[]` → `month` (formato "2026-01" → "Ene"), `positionsCreated`, `cvUploads`, `vacanciesCreated`. Ajustar el cálculo de `MAX_Y_VALUE` dinámicamente (hoy está fijo en 14).
3. Adaptar `DashboardStats` en `src/types/dashboard.types.ts` a la forma real del backend (o crear un adaptador que traduzca la respuesta al modelo actual del componente).
4. Estados de carga/error/empty (hoy no hay).

### 7.2 — Responsive

**Problema:** padding y `min-h` fijos (`Dashboard.tsx:49,79`) desbordan en pantallas pequeñas y obligan a scroll horizontal/márgenes rotos.

**Pasos:**
- Revisar `min-h-[350px] xl:min-h-[450px]` de la gráfica → usar altura flexible o `aspect-ratio`, permitir que colapse en móvil.
- Verificar que las grillas (`grid-cols-4`, `grid-cols-3`) caen a 1–2 columnas en breakpoints pequeños (ya usan `sm:`/`lg:`; revisar el rango intermedio).
- Asegurar que el contenedor no fuerza ancho mayor al viewport (nada de anchos fijos). Probar en 360px, 768px, 1024px, 1440px.

### 7.3 — Accesos rápidos = atajos a los historiales

**Problema:** cada `MetricCard` dibuja una flecha "→" pero no navega. **Deben ser atajos directos a los historiales.**

**Mapeo:**
| Tarjeta | Destino |
|---|---|
| Total Posiciones | `/position-history` |
| Departamentos Activos | `/department-history` |
| Candidatos en Pool | `/candidates-history` (o `/cv-history`) |
| Vacantes Abiertas | `/vacancy-history` |

**Pasos:**
1. `MetricCard` acepta una prop `to: string` (o `onClick`).
2. Envolver la tarjeta en un `Link`/`onClick` con `useNavigate` y estilos de cursor/hover; la flecha "→" refuerza que es clicable.
3. En `Dashboard.tsx`, pasar el `to` correspondiente a cada métrica según la tabla.

### ✅ Criterio de aceptación EPIC 7

Métricas y gráficas con datos reales del usuario; sin scroll indebido en móvil; cada tarjeta navega a su historial.

## EPIC 8 — Panel de Administración

Archivos: `src/pages/AdminPanel.tsx`, `src/components/admin/*`, `src/types/admin.types.ts`, nuevo `src/services/api/admin.api.ts`.
API: §6 — **admin-only** (`role: ADMIN`, si no `403`).

### 8.1 — Crear el servicio `admin.api.ts`

Nuevo archivo `src/services/api/admin.api.ts`:
```ts
import { apiClient } from "./apiClient";

export const adminApi = {
  // GET /admin/stats — métricas GLOBALES de la plataforma (§6, §9.4)
  getStats: () => apiClient("/admin/stats", { method: "GET" }),

  // GET /admin/users?page&limit — { users: User[], meta }
  getUsers: (page = 1, limit = 50) =>
    apiClient(`/admin/users?page=${page}&limit=${limit}`, { method: "GET" }),

  // PUT /admin/users/:id/role — body { role: "ADMIN" | "USER" }
  updateRole: (id: number | string, role: "ADMIN" | "USER") =>
    apiClient(`/admin/users/${id}/role`, {
      method: "PUT",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({ role }),
    }),

  // DELETE /admin/users/:id
  deleteUser: (id: number | string) =>
    apiClient(`/admin/users/${id}`, { method: "DELETE" }),
};
```

### 8.2 — [Pendiente de conectar] Conectar `AdminPanel` y módulos

**Problema:** hoy usan `mockUsers` (`UserTableModule.tsx:6`), loader `setTimeout`, y el buscador no tiene `onChange`.

**Pasos:**
1. Elevar el estado a `AdminPanel`: cargar `adminApi.getStats()` y `adminApi.getUsers()` al montar (quitar el `setTimeout`).
2. `StatsModule` recibe las stats reales; `UserTableModule` recibe `users` por props (no mock) y un `onChange` real para el buscador (filtrar por nombre/email en cliente, o `getUsers` con búsqueda si existiera).
3. `RoleUpdateModule` → `adminApi.updateRole(id, role)`; `UserDeleteModule` → `adminApi.deleteUser(id)`. Refrescar la lista tras cada acción.
4. Estados de carga/error/empty.

### 8.3 — Casing de roles

**Problema:** la API usa `ADMIN`/`USER`; `admin.types.ts` tipa `'admin' | 'user'`.
**Pasos:** unificar al enum del backend (`ADMIN`/`USER`) en `AdminUser.role` y en la UI mapear a etiqueta visible ("Admin"/"Usuario"). Ajustar los módulos de rol.

### 8.4 — No confundir stats globales con dashboard

`GET /admin/stats` es **global** (toda la plataforma); `GET /dashboard` es por usuario (§9.4). Mantenerlos como fuentes separadas; el panel admin usa `/admin/stats`.

### ✅ Criterio de aceptación EPIC 8

El panel lista usuarios reales (paginados), permite cambiar rol y eliminar, y muestra stats globales. Un `USER` que entre recibe manejo de `403` (ver EPIC 9.3).

## EPIC 9 — Auth / control por rol

Archivos: `src/components/context/AuthContext.tsx`, `src/pages/Login.tsx`, `src/layouts/Sidebar.tsx`, `src/App.tsx`.
API: §0/§1 — el token contiene `{ userId, role }` y el login devuelve `user.role`.

### 9.1 — Guardar el `role` en el AuthContext

**Problema:** `UserData` no guarda `role`, así que no se puede gatear admin.

**Pasos:**
1. En `AuthContext.tsx`, agregar `role: "ADMIN" | "USER"` a `UserData`.
2. Cambiar la firma de `login` para recibir el rol: `login(email, token, role)`.
3. En `Login.tsx` (`handleSubmit`), pasar el rol de la respuesta: `login(email, token, data.user.role)`.
4. Persistir `role` en `localStorage` junto con `tm_user`.

### 9.2 — Sidebar: admin primero, con ícono propio y solo para ADMIN

**Archivo:** `src/layouts/Sidebar.tsx` (~líneas 55-60).
**Pasos:**
1. Mover el item "Administración" al **primer** grupo del menú (antes de Dashboard, o en su propio grupo superior), según el mockup.
2. Asignar un **ícono propio** (ej. `Shield` de lucide, o un SVG de admin) en vez de `Icons.sidebar.dashboard`.
3. Mostrarlo **solo si** `user?.role === "ADMIN"`:
   ```tsx
   const isAdmin = user?.role === "ADMIN";
   // filtrar el grupo/item de admin si !isAdmin
   ```

### 9.3 — (Opcional) Proteger la ruta `/admin`

En `App.tsx`, envolver `/admin` en un guard que redirija a `/dashboard` si `role !== "ADMIN"`, para evitar el `403` crudo del backend.

### ✅ Criterio de aceptación EPIC 9

Tras login, el rol queda disponible; "Administración" aparece de primero, con ícono propio, y solo para administradores.
